# معماری و تصمیم‌ها

## مسئله

پکیج رسمی `MetaTrader5` برای پایتون یک DLL ویندوزی (`MT5APY`/ترمینال) را بارگذاری
می‌کند. روی لینوکس فقط با Wine و پایتون ویندوزی کار می‌کند؛ نتیجه: دو اکوسیستم موازی،
مسیرهای عجیب، پورت سریال‌مانند، کرش‌های ترمینال و دیباگ نشدنی.

هدف: پایتون/هوش مصنوعی روی لینوکس بومی، ولی دسترسی کامل و امن به همان ترمینالی که
کاربر از قبل دارد.

## تصمیم اصلی

**منطق ویندوزی را همان‌جا که هست نگه دار؛ مرز را روی یک سوکت بگذار.**

```
[MCP client] --stdio--> [trade_mcp server] --TCP JSON--> [MQL5 EA] --API--> [MT5 terminal] --> broker
   (مدل AI)               (لینوکس، بومی)                 (داخل ترمینال، هر جا)
```

نتیجه:

- `OrderSend`، `CopyRates`، `SymbolInfo*` و هر API دیگری داخل ترمینال اجرا می‌شود
  (تنها جای قانونی‌اش).
- پایتون هیچ DLL، هیچ COM و هیچ مسیر ویندوزی نمی‌شناسد.
- ترمینال می‌تواند Wine، ویندوز، VPS یا حتی ماشین دیگری باشد.

## گزینه‌هایی که رد شدند

| گزینه | چرا نه |
|---|---|
| `MetaTrader5` pip + Wine + پایتون ویندوزی | همان درد اصلی: دو پایتون، مسیرهای شکننده، وابستگی به نسخه‌ی Wine |
| `mt5linux` / RPC روی پایتون ویندوزی | مشکل را یک لایه عقب‌تر می‌برد، حلش نمی‌کند |
| EA + `WebRequest` (HTTP polling) | نیازمند whitelist در تنظیمات، تأخیر polling، بد برای پاسخ‌های بزرگ |
| EA + فایل‌های مشترک (FileOpen read/write) | شکننده، بدون قفل، روی Wine رفتار عجیب |
| MetaApi / Alpine و سرویس‌های ابری | هزینه‌ی ماهانه، وابستگی به شخص ثالث، تأخیر، کنترل کمتر |
| cTrader / OANDA و تغییر بروکر | تغییر حساب و پلتفرم؛ برای «همین MT5 فعلی» جواب نیست |

## لایه‌ها

| لایه | فایل | مسئولیت |
|---|---|---|
| MCP | `server.py` | تعریف ۱۸ ابزار + ۲ پرامپت، تبدیل خطا به JSON، دستورالعمل مدل |
| دامنه | `analysis.py`, `indicators.py`, `risk.py`, `execution.py` | تحلیل قطعی، سناریوسازی، حجم، گاردها، جریان دو مرحله‌ای |
| اتصال | `bridge/server.py` (TCP)، `bridge/client.py` (تایپ‌شده + کش)، `bridge/mock.py` | پروتکل، درخواست/پاسخ، بک‌اند ساختگی |
| ذخیره | `store.py` | SQLite: پیشنهادها، معاملات، یادداشت‌ها |
| ترمینال | `mt5-connector/TradeMCPConnector.mq5` | سوکت کلاینت، پارس JSON، اجرای دستورها روی API متاتریدر |

اصل: لایه‌های بالایی هیچ‌وقت مستقیم با سوکت حرف نمی‌زنند و لایه‌ی پایین هیچ‌وقت
تصمیم معاملاتی نمی‌گیرد.

## چرا پایتون سرور است و EA کلاینت؟

- EA با `SocketConnect` خودش وصل می‌شود و در صورت قطعی، با فاصله‌ی ۳ ثانیه دوباره
  تلاش می‌کند. پس می‌توانی سرور MCP را هر بار ری‌استارت کنی بدون دست‌زدن به MT5.
- روی سمت پایتون، `asyncio` هم‌زمان چند درخواست را با `id` تطبیق می‌دهد.
- فایروال و مجوز: یک سوکت خروجی از ترمینال، ساده‌ترین حالت ممکن است.

## جریان یک معامله

```
مدل  → analyze_market ─────► کندل‌ها/اندیکاتورها → سناریو (entry, SL, TP1/2, RR, حجم)
مدل  → propose_order  ─────► اعتبارسنجی کامل + ثبت در SQLite (status=pending, TTL=180s)
انسان → «تأیید می‌کنم»
مدل  → confirm_proposal ───► چک مجدد: مجوز معامله؟ منقضی نشده؟ قیمت > ۱R حرکت نکرده؟
                              → trade_open در EA → OrderSend → retcode
                              → status=executed + رکورد در جدول trades
```

`confirm_proposal` هیچ‌وقت توسط مدل «حدس» زده نمی‌شود: دستورالعمل سیستم به آن صریح
می‌گوید بدون تأیید انسانی اجرا نکن، و اجازه‌های OpenCode هم می‌توانند همان ابزار را
`ask` کنند.

## گاردهای ریسک (لایه‌ی سرور، نه لایه‌ی مدل)

`risk.validate_order` قبل از هر سفارش بررسی می‌کند:

1. `ALLOW_TRADING` روشن است؟
2. نماد در لیست سفید است؟ (با پشتیبانی از پسوند بروکر: `XAUUSD.a`)
3. حجم بین min/max بروکر و روی شبکه‌ی step است؟ زیر `MAX_LOT` هست؟
4. تعداد پوزیشن باز زیر سقف است؟
5. اسپرد از سقف عبور نکرده؟
6. فاصله‌ی استاپ از `trade_stops_level` و اسپرد بیشتر است؟ سمت درست است؟
7. ریسک تا استاپ از `MAX_RISK_PERCENT` بیشتر نمی‌شود؟
8. مارجین آزاد کافی است؟

اگر هر «blocker» وجود داشته باشد، پیشنهاد ساخته می‌شود ولی قابل تأیید نیست.

## چرا تحلیل قطعی و جدا از مدل؟

مدل‌ها در محاسبه‌ی ATR/RSI/RR و ضرب و تقسیم حجم بد هستند و «عدد از هوا» می‌سازند.
پس هر عددی که به کاربر می‌رسد از کد می‌آید:

- `indicators.py` → EMA/RSI/ATR/ADX/Bollinger/Donchian/Swing/شیب رگرسیون (بدون numpy)
- `analysis.py` → رای‌گیری چند تایم‌فریمی، رژیم نوسان، سطوح کلیدی، سناریو با قیمت
- `risk.py` → حجم از تیک‌ولیو، ریسک نقدی، مارجین

مدل فقط تفسیر می‌کند: چه چیزی تأیید می‌کند، چه چیزی تناقض دارد، چه چیزی ایده را باطل
می‌کند. این کار توهم (hallucination) عددی را عملاً حذف می‌کند.

## بک‌اند mock

`bridge/mock.py` همان پروتکل را با قیمت‌های هارمونیک قطعی (نه تصادفی per-call) پیاده
می‌کند: هر timestamp همیشه همان کندل را می‌دهد، پس تحلیل چندتایم‌فریمی و تست‌ها پایدار
می‌مانند. هر پاسخ `"mock": true` دارد تا با داده‌ی واقعی اشتباه نشود.

## نقطه‌های توسعه

- `bridge/base.py` یک `Protocol` است: برای بروکر دیگر (cTrader، OANDA) فقط یک
  transport جدید بنویس؛ ابزارها و تحلیل دست‌نخورده می‌مانند.
- `execution.py` تنها جایی است که سفارش ارسال می‌شود: هر سیاست جدید (ساعت معامله،
  هم‌بستگی نمادها، حداکثر ریسک روزانه) همین‌جا اضافه می‌شود.
- `store.py` می‌تواند به پایه‌ی بک‌تست و گزارش‌گیری تبدیل شود.
